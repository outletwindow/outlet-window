# Courier proof-of-delivery storage

The API supports an S3-compatible private object store (AWS S3 or Cloudflare R2)
for courier delivery evidence. Storage is deliberately optional: when these
variables are absent, proof-upload endpoints remain unavailable (503) rather
than accepting unverified evidence.

## Runtime configuration

Configure all required variables together in the API runtime secret manager:

- `COURIER_PROOF_S3_ENDPOINT`: HTTPS S3 endpoint. For R2, use the account's S3 API endpoint.
- `COURIER_PROOF_S3_BUCKET`: private bucket name.
- `COURIER_PROOF_S3_REGION`: bucket region; R2 uses `auto`.
- `COURIER_PROOF_S3_ACCESS_KEY_ID`: dedicated access key.
- `COURIER_PROOF_S3_SECRET_ACCESS_KEY`: dedicated secret.
- `COURIER_PROOF_S3_SESSION_TOKEN`: optional temporary credential token.

Do not commit credentials or place them in browser configuration. Do not reuse
the platform's general-purpose storage credentials.

## Bucket and access controls

- Keep the bucket private; disable public access and public object ACLs.
- Give the API identity only the object permissions needed for the
  `courier-delivery-proof/*` prefix: create objects and read object metadata.
- Do not grant bucket administration, object deletion, or public-read access.
- Keep object keys generated by the API. Clients must never choose object keys.
- Configure a lifecycle policy to expire abandoned, unverified uploads.
- Restrict CORS to the deployed courier web origins and allow only PUT with
  the `Content-Type` and `x-amz-checksum-sha256` request headers.
- The presigned URL expires after five minutes.

## Upload verification

The client hashes the image bytes with SHA-256, requests an upload URL, then
uploads using the exact `Content-Type` and `x-amz-checksum-sha256` headers
returned by the API. S3 validates the checksum during PUT. Finalization performs
a signed HEAD request and compares the stored content type, byte length, and
server-reported SHA-256 with the intent persisted in PostgreSQL. Only then does
the API append immutable `proof_of_delivery` evidence.

A task cannot be marked delivered without that verified evidence. The application
does not store image bytes in PostgreSQL and does not expose permanent public
image URLs.

## Validation before production

1. Provision a dedicated private test bucket and restricted test credentials.
2. Configure the variables in a non-production environment.
3. Test upload with JPEG, PNG, and WebP; test wrong checksum, wrong MIME type,
   wrong length, missing object, expired URL, and cross-tenant task IDs.
4. Confirm that an unverified or expired upload cannot create evidence or mark
   a task delivered.
5. Rotate or revoke test credentials after validation.

The adapter is S3-compatible and covered by unit tests, but production provider
credentials, bucket policy, CORS, and a real end-to-end upload have not yet
been configured or verified.
